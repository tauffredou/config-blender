# 3. Runtime nature and sandboxing

configblender runs at **runtime** — a live component inside the cluster, not an artifact generator frozen at build-time/CI. Dynamic layers (scripts) are therefore evaluated continuously in the cluster, not once and for all in a pipeline.

Direct consequence: running arbitrary scripts at runtime inside the cluster requires **strict sandboxing** of dynamic layers — this isn't optional once the runtime choice is made.

The initial reference model was the **Jenkins Script Security Plugin**: every method call, object construction, or field access is checked against a whitelist of approved operations, with everything else rejected by default. The principle (deny by default anything not explicitly permitted) is kept, but **implementing it via a method whitelist is not desired**: maintaining a list of individually approved APIs for general-purpose languages like Python or Node is judged too operationally heavy.

**Decision made: the choice of Starlark ([02-resolution-model.md §2.6](02-resolution-model.md)) directly answers this constraint.** Starlark is **hermetic by construction** — no file, network, or system-clock access, unless the Go controller explicitly exposes them in the "predeclared" environment given to the script. The security model therefore becomes **capability-based rather than blacklist/whitelist**: configblender only exposes to a dynamic layer the accumulated input configuration and Starlark's basic primitives (string/list/dict manipulation, no I/O) — there is nothing dangerous to whitelist since nothing dangerous is exposed. This is the coarse grain being aimed for, obtained as a property of the language rather than a mechanism to build.

- **Resource-exhaustion protection**: `go.starlark.net` provides an execution-step limit (computation steps, `Thread.SetMaxExecutionSteps`) and thread cancellation via timeout (`Thread.Cancel`) — used to bound the time/cost of a dynamic layer in the reconciliation loop ([04-kubernetes.md](04-kubernetes.md)), preventing an infinite-loop script from blocking the controller. Implemented (`resolve.StarlarkOptions`), tested (step limit triggered on an unbounded loop).
- **Remaining defense in depth**: Starlark's guarantees rest on the correctness of the `go.starlark.net` implementation itself (a widely used library — notably used by Bazel to run untrusted BUILD code — but not formal proof of the absence of bugs). Running the configblender controller pod with reduced privileges (non-root, read-only rootfs, minimal Linux capabilities) remains a reasonable precaution, but applies to the pod as a whole rather than a per-script sandbox mechanism to design.

**Complementary approach — GitOps**: a PR/CODEOWNERS review before a script becomes executable by configblender is still relevant, but its role changes with Starlark: the question is no longer so much "prevent a script from accessing dangerous resources" (already covered by the language's lack of ambient authority) as "catch a logic error or an undesirable config value before it reaches an environment" — a correctness/change-management goal rather than a critical security safeguard. Both mechanisms remain complementary, but GitOps is no longer a necessary condition for sufficient sandboxing: Starlark already provides the security baseline for the MVP.

Layer content (static and Starlark scripts) stays versioned in a Git repository regardless of whether formal review is adopted — see [05-recipe-and-crd.md](05-recipe-and-crd.md).
