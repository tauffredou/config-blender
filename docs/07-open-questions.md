# 7. Open questions

- **Authentication/TLS between a controller and the central service** ([04-kubernetes.md §4.2](04-kubernetes.md)): `internal/centralclient` calls the central service over plain HTTP, with no authentication or encryption. Tolerable for a single-cluster test (intra-cluster traffic), but needs to be settled before a real multi-cluster deployment where this traffic can leave the cluster (mTLS, token, or HTTPS at minimum). Distinct from the UI/CLI write token (5.3bis), which already protects PUT/rollback.
- **UI authentication beyond a single shared token** ([05-recipe-and-crd.md §5.3bis](05-recipe-and-crd.md)): `CONFIGBLENDER_WRITE_TOKEN` is a single secret shared by anyone who needs to write — no distinct users, no audit of who performed which `put`/rollback (version history knows *when*, not *who*), no rotation other than redeploying the central service with a new token.
- **Local vs network type difference** (`internal/centralclient`): a tree resolved locally yields native Go integers (`int`) and explain leaves typed as `resolve.Provenance`, whereas a tree received from the central service (JSON) yields `float64` for numbers and explain leaves as `map[string]any` (`encoding/json` decodes any object into an `any` value with no knowledge of `Provenance`). No consequence for the CLI's current YAML output (both serialize the same way), but worth keeping in mind if downstream code ever does a direct `switch`/type assertion on `resolve.Result`.
- **Concrete write-side GitOps mechanism** ([05-recipe-and-crd.md §5.3](05-recipe-and-crd.md)): `configblender put` applies a Spec file directly to the database — chosen as the only write path for v1 (no push API). Still to be designed: who/what runs this `put` in production (direct access to the central service's database via a shared volume/`kubectl exec`, a CI step, or a future automatic sync mechanism from a Git repo of Specs); and whether an authenticated write API will ever be needed beyond v1.
- Backup/durability strategy for the Recipe database ([05-recipe-and-crd.md §5.2](05-recipe-and-crd.md)) — configblender is a stateful service, not a simple stateless controller.
- ~~Per-repo Git credentials rather than a single global set~~ — **resolved**: `internal/gitsourcedb` registers named Git sources (`{name, repo}`, no credentials), a `recipe.LayerSpec` references one by name (`LayerSource.SourceRef`) instead of embedding a raw repo URL, and `internal/gitauth.FromSources` resolves each source's own credentials from per-source env vars (`GIT_TOKEN_<NAME>` etc., sanitized from the source name), falling back to the single global credential (`FromEnv`) when no per-source override exists. Credentials still only ever come from the environment — the registry itself carries no secret material, so nothing sensitive passes through the API/webui/CLI that manage it. Still open: feeding per-source env vars from several K8s Secrets automatically (currently one Secret's worth of env vars per source, manually named to match).
- SSH host-key verification (`gitsource.SSHAuthMethod`) — not explicitly configured, default `go-git` behavior.
- Can a Recipe be referenced by several binding CRDs (sharing sources across several targets)? No opinion for now, left open. Distinct from the Git-source registry above (which shares *Git repos* across layers/Recipes) — this is about sharing a *Recipe* across several ConfigBlend/binding CRDs, à la `SecretStore`/`ExternalSecret` ([05-recipe-and-crd.md §5.4](05-recipe-and-crd.md)).
- Precise list of Starlark primitives exposed in the "predeclared" environment beyond the accumulated configuration ([03-security.md](03-security.md)): formatting, hashing... to be confirmed without reintroducing I/O.
- Default values for the execution-step limit and per-dynamic-layer timeout ([03-security.md](03-security.md)) — a configuration detail, not a design question.
- Exact `mergePolicy` syntax: nested paths/wildcards beyond a simple dot-notation path ([02-resolution-model.md §2.1](02-resolution-model.md)).
